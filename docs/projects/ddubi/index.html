Apache Spark · 최신 관측 처리

Spark 배치에서 가장 최근 관측을 골라도 다음 배치에 이전 시각의 관측이 도착할 수 있었습니다. 이때 오래된 값이 최신값을 덮지 않도록 Redis에 기록하는 순간 기존·신규 관측 시각을 비교하는 방식으로 보완했습니다.

FastAPI · 예측 요청 검증

실제 매핑 구간을 로컬 FastAPI TestClient에서 조회했습니다. 예측값이 있어도 이력 표본이 없는 구간에는 데이터 부족 표시가 붙었고, 같은 구간의 날짜를 지원 범위 밖으로 바꾸자 예측값이 비었습니다. 이 결과로 경로 계산에서 제외할 조건을 확인했습니다.

제가 맡은 일

수집 담당자와 연산 입력을 조율하고, 실제 경로 응답을 제공했습니다. 5002번은 제가 상세 화면을 열어 예약 표기와 정류장 순서를 확인했습니다. 매핑 코드·검증기와 모델 학습·실행에는 AI의 도움을 받았습니다.

판단하고 바꾼 과정

같은 번호에 노선 세 개

공식 자료에는 5002A, 5002B, 5002(예약)가 있었습니다. 출발·도착 좌표가 가깝더라도 다른 노선의 시간을 붙일 수 있었습니다. 상세 화면의 예약 표기와 강남역에서 뱅뱅사거리까지의 정류장 순서를 공식 자료와 맞췄습니다.

확인한 구간에만 적용

다른 날짜와 방향까지 같은 번호로 승인하면 오연결이 생깁니다. 검토한 경로, 날짜, 마스터 버전과 공간 검사가 일치할 때만 공식 ID를 쓰도록 범위를 정했습니다. 개발 경로 4개에서 마지막 대안 한 건을 추가로 확인했고 기존 연결이 달라진 건은 0개였습니다.

예측 시점에 구할 수 있는 입력으로 비교

수집 담당자와 API 한도와 누락 시간대를 확인했습니다. 승하차 인원 열을 추가하고도 실제로 연결된 값이 0%였던 실험을 본 뒤 조인 키와 입력 가용 시점을 따로 살폈습니다. 시간 순서로 나눈 동일 검증 999,894행에서 구간별 평균 절대 오차(MAE)가 가장 낮은 LightGBM을 골랐습니다.

같은 모델에서 읽기 비용을 따로 측정

같은 10개 구간을 넣고 참조 표를 매번 읽는 방식과 256MiB 캐시를 쓰는 방식을 비교했습니다. Windows 로컬의 조건별 반복 3회 평균이 1.8675초에서 1.6305초로 줄었고 예측값은 같았습니다. 대신 프로세스 최대 메모리는 1,370.1MiB에서 1,542.9MiB로 늘었습니다.
