어떤 프로젝트인가요?

사진·영상에 소비 금액과 카테고리를 함께 기록하고, 월별 소비 내역과 분석을 확인하는 서비스입니다.

초기 서비스와 데이터 구조를 팀원과 함께 기획했습니다. 이후 화면의 누락, API 입력 조건, 데이터 생성·저장 상태를 대조하고, 소비 기록과 분석이 이어지는 흐름을 점검했습니다.

THE QUESTION

분석을 만들기 전에, 기록이 없는 달부터 생각했습니다.

분석 화면에 문장이 나온다고 기능이 완성되는 것은 아니었습니다. 어떤 데이터를 넘기는지, 결과를 다시 볼 수 있는지, 호출이 실패해도 사용자가 상황을 이해할 수 있는지가 필요했습니다.

판단하고 바꾼 과정

01

실제 집계 값으로 분석 요청

월별 총 소비액과 카테고리별 집계 값을 입력으로 정리했습니다. 서버에서 GMS의 LLM API를 호출하고, 클라이언트에 API 키를 노출하지 않는 구조를 적용했습니다.

02

생성·저장·조회까지 이어서 확인

분석 결과를 구조화된 JSON으로 받고, 생성 후 저장한 결과를 최신 분석과 이전 이력에서 확인하는 흐름을 점검했습니다. 설명과 실제 구현의 차이도 함께 확인했습니다.

03

실패 원인별로 처리 분리

키 누락, API 호출 오류, 응답 해석 실패를 구분했습니다. 정상 분석을 만들 수 없으면 정해진 규칙으로 대체하고, 소비 기록이 없는 경우에는 데이터 부족 상태를 표시하도록 했습니다.

04

처음 하는 Git 협업에 기준 세우기

두 사람이 어떤 방식으로 코드를 합칠지 고민했습니다. 삼성청년SW·AI아카데미 멘토링 게시판에서 현직자의 Git 협업 규칙을 참고해 팀 작업에 적용했습니다.

정상 응답과 실패 상황을 함께 다룬 분석 흐름

생성 → 조회

한 번 만든 분석을 저장하고 다시 확인

오류별 처리

키·호출·응답 해석 실패를 구분

가입·소비 기록·월별 분석을 화면, API, 데이터 제약으로 나누어 확인할 기준을 구체화했습니다. 다른 PC에서 이미지가 누락되는 문제도 확인해 저장 방식 변경을 요청했습니다.

확인 범위

초기 기획은 공동으로 진행했습니다. 전체 서비스의 단독 구현이나 추천 품질·응답 속도 개선을 주장하지 않습니다. 기존 이미지의 자동 복구까지 확인한 것은 아닙니다.

다음 작업에 가져갈 기준

생성된 문장만 보기보다 실제 입력과 저장 결과, 예외 상황을 함께 확인해야 사용자가 다시 찾을 수 있는 기능이 된다는 점을 배웠습니다.
