가입에서 첫 소비 기록까지

계정이 생겨도 첫 소비를 기록할 수 없었습니다.

문제
가입 화면에서는 이메일이 선택 항목처럼 보였고, 프로필 저장에 실패하면 계정만 남을 수 있었습니다. 가입을 마쳐도 카테고리 목록이 비면 첫 기록을 작성할 수 없었습니다.
개선 과정
가입 오류와 빈 목록을 확인하고 팀원과 만든 ERD를 실제 모델과 대조하도록 요청했습니다. 가입 폼과 서버의 필수값을 맞추고, 계정·프로필을 함께 저장하거나 함께 되돌리도록 수정 조건을 정했습니다.
결과
가입 저장을 하나의 트랜잭션으로 묶고 기본 카테고리 8종을 준비했습니다.
당시 소비 기록 생성·조회·수정·삭제를 포함한 개발 단계에서 테스트 25개와 빌드 통과가 보고됐습니다. 브라우저에서 가입부터 첫 게시까지 전 과정을 확인한 수치는 아닙니다.

소비 사진 보관

다른 PC에서 피드를 열자 금액과 글은 남고 사진만 사라졌습니다.

  1. 새 PC에서 피드 확인
  2. SQLite의 경로와 실제 업로드 파일 대조
  3. 새 업로드를 DB에 저장
  4. API의 이미지 응답 확인
문제
SQLite에는 업로드 파일의 경로만 남아 있었습니다. DB를 복사해도 새 PC에는 그 경로가 가리키는 사진이 없었습니다.
개선 과정
사진도 소비 기록과 함께 옮길 수 있도록 변경을 요청했습니다. 새 업로드의 바이트를 Django BinaryField에 저장하고, API가 화면에서 표시할 수 있는 data URL로 반환하는 방식을 확인했습니다.
결과
새로 올린 사진은 SQLite 파일에 소비 기록과 함께 저장됩니다.
6월 23일 코드에서 저장과 응답 경로를 확인했습니다. 기존 경로형 사진은 원본 파일이 따로 필요하며, 이미지가 포함된 목록 응답의 크기와 속도는 비교 측정하지 않았습니다.

문제
두 경우 모두 AI 분석 문장이 나오지 않습니다. 하지만 소비 내역이 있는 달에는 외부 호출이 실패해도 이미 계산한 총액과 카테고리별 집계를 쓸 수 있었습니다.
개선 과정

결과

6월 16일 기록에서 두 분기와 대체 규칙을 확인했습니다. 금액 기준이 개인의 소득이나 소비 성향에 얼마나 잘 맞는지는 평가하지 않았습니다.

목표
팬은 자신의 차례를 기다리고, 호스트는 다음 팬을 호출해 해당 통화에 바로 입장할 수 있게 하는 것이 목표였습니다.

적용 맥락과 선택 이유

LiveKit

sessionStorage
장비 점검과 통화는 서로 다른 화면입니다. 선택한 장치 ID를 탭 안에서 유지하기 위해 sessionStorage에 저장하고 입장 시 다시 읽었습니다.

팬 대기실

문제 해결 사례

팬미팅 생성 API 연동

응모를 껐는데도 행사 생성 요청이 계속 400 오류로 돌아왔습니다.

문제
문서대로 정원을 생략하면 서버의 필수값 검사에서 막혔고, 기본값 1을 보내면 비활성 응모의 정원은 0이어야 한다는 규칙에 걸렸습니다.
개선 과정
실패한 요청 본문을 직접 제시하고 팀 브랜치의 서버 코드를 대조하도록 요청했습니다. 서버의 입력 검사 순서를 확인한 뒤 프런트에서 정원 0과 빈 응모 날짜를 명시해 보내도록 보완했습니다.
결과
수정한 프런트엔드의 린트·타입 검사·빌드가 통과했습니다.
어떤 입력이 두 검사를 만족하는지 코드로 확인했습니다. 권한 있는 계정으로 행사 생성까지 성공했는지는 당시 확인하지 못했습니다.

호스트의 다음 팬 호출

혼자 진행하는 호스트가 팬 한 명을 만날 때마다 화면을 옮겨야 했습니다.

문제
다음 팬 호출은 매니저 화면에, 영상 방 입장은 인플루언서 화면에 있었습니다. 호출 응답에 들어 있는 개별 통화 ID도 입장에 쓰이지 않았습니다.
개선 과정
호스트에게 허용된 호출·메모·장비 점검·입장을 한 콘솔에 모으고, 호출 API가 반환한 통화 ID를 입장 대상에 연결했습니다.
결과
호출한 팬의 방으로 같은 운영 화면에서 입장하는 흐름을 연결했습니다.
담당 프런트엔드의 호출 응답 처리와 입장 경로에서 확인한 결과입니다. 실제 행사에서 팬 전환에 걸리는 시간은 측정하지 않았습니다.

영상 통화 입장 복구

입장 권한이 있는데도 행사 상태 조회 한 번이 통화를 막았습니다.

문제

개선 과정
두 요청을 함께 보내되 결과는 각각 판정하도록 보완했습니다. 토큰 발급이 실패하면 입장을 중단하고, 상태 조회만 실패하면 영상 방과 오류 안내를 함께 표시한 뒤 상태를 다시 조회하도록 했습니다.

키링 내부 로직 설계

여러 사람이 스쳐 갈 때, 무엇을 통신 거리 안에서 끝내야 할까?

  1. 가상 키링의 동시 교환 재현
  2. 제어 메시지만 반복되는 구간 확인
  3. 재전송 시 프로필도 전달
  4. 양방향 계산 확인
문제
한 상대의 매칭을 계산하는 동안 다른 키링이 통신 범위를 벗어날 수 있었습니다. 동시 교환 시험에서는 한쪽이 제어 메시지만 반복해 계산에 필요한 상대 프로필을 받지 못하는 경우도 나왔습니다.
개선 과정
짧은 만남 동안에는 프로필 수신을 우선하도록 설계했습니다. 수신을 마친 입력은 상대별 매칭 대기 큐에, 확정된 만남은 앱 전달 큐에, 판정을 끝내지 못한 건은 오류·검증 큐에 넣었습니다. 제어 메시지를 재전송할 때에도 프로필을 함께 보내도록 송신 흐름을 보완했습니다.
결과
PC에서 가상 키링 10개의 동시 교환을 시험했습니다.
수정 후 상대 프로필 교환에서 양방향 계산까지 이어졌고, 기준 입력 37건에서 펌웨어의 C 계산값이 참조값과 일치했습니다. 여러 사람이 실제로 스쳐 갈 때의 수신 성공률은 측정하지 못했습니다.

개선 과정
추가 납땜 전에 브레드보드에서 LED·모터·버튼을 따로 점검하는 시험안을 마련했습니다. EasyEDA로 보드는 소켓에 꽂고 외부 모듈은 커넥터로 교체하는 PCB를 설계했습니다. 수령한 D3.1 기판과 모듈의 핀 간격이 달라 연결선을 직접 압착하고 핀 순서를 대조했습니다.

제작한 D3.1 기판에서 LED 점등과 모터 진동을 확인했습니다.
설계 파일에서는 배선 규칙 검사 오류 0건과 50개 핀의 연결 일치를 확인했습니다. 실물에서는 빛과 진동을 관찰했고, 밝기와 전류는 계측하지 않았습니다.
