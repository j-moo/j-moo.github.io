행사 상태 조회가 실패해도 영상 방을 열 수 있을까?

유효한 입장 토큰을 받아도 타이머에 쓰는 행사 상태 조회가 실패하면 영상 방이 열리지 않았습니다.

AI를 활용한 작업

AI와 함께 두 요청의 오류 분기를 수정하고, 상태 조회만 실패시키는 회귀 테스트를 보완했습니다.

내 판단과 검증

입장 토큰은 통화에 필수이고 행사 상태는 타이머·종료 안내에 쓰입니다. 토큰이 유효한 상황에서는 영상 방을 열고 보조 정보의 오류를 따로 안내하도록 조건을 나눴습니다.

검증 결과

영상 방 컴포넌트와 오류 안내가 같은 화면에 표시됐습니다.

미디어 컴포넌트를 대체한 프런트엔드 테스트입니다. 실제 카메라·마이크 송수신 품질은 이 결과에 포함되지 않습니다.

오차가 줄었다. 승객 수가 정말 쓰였을까?

승객 수를 추가한 모델의 예측 오차가 줄었다는 보고를 받았습니다. 오차만 보면 승객 수가 예측에 도움이 된 것처럼 보였습니다.

AI를 활용한 작업

AI와 함께 과거 운행시간을 이용한 입력을 구성하고, 시간순으로 나눈 자료에서 학습 방식을 비교했습니다. 승객 수를 추가한 실험에서는 성능 보고와 실제 학습에 들어간 표본을 다시 대조하도록 했습니다.

내 판단과 검증

승객 수가 학습 행에 얼마나 연결됐는지 확인하니 결합률이 0%였습니다. 결합 오류를 고친 뒤 같은 내부 검증 조건에서 승객 수를 넣은 모델과 뺀 모델을 비교했습니다.

검증 결과

이 비교에서는 승객 수를 넣자 오차가 0.016초 커졌습니다. 승객 수를 개선 요인으로 보고하지 않았습니다. 이후에는 입력 결합률과 실제 학습 행 수를 오차와 함께 확인했습니다.

두 수치는 같은 내부 검증에서 측정한 구간 평균시간 오차입니다. 전체 경로의 도착시각이나 이용자 대상 성능은 별도로 측정해야 합니다.

키링의 기록이 사라졌을까, 출력만 빠졌을까?

AI를 활용한 작업

기존 등록·만남 기록을 그대로 둔 채 상대별 상태를 읽을 수 있어야 한다는 조건을 주었습니다. AI를 활용해 로그와 펌웨어를 대조하고 읽기 전용 진단 기능과 출력 순서를 보완했습니다.

내 판단과 검증

실물에서 긴 목록을 조회하자 일부 줄이 빠졌습니다. 로그 대기열의 처리 속도를 확인하고 앞선 줄을 내보낸 뒤 다음 줄을 출력하도록 수정했습니다. 보드에서 예상 건수와 종료 표시를 함께 확인했습니다.

검증 결과

세 종류의 조회가 총 8회 모두 끝까지 응답했습니다. 조회 전후 등록 영역과 만남 기록 영역의 해시도 각각 일치했습니다. 기록을 보존하면서 상대별 상태를 읽을 수 있게 됐습니다.

시험 범위는 한 보드의 진단 출력과 저장 내용 보존입니다. 무선 매칭 성공률은 이 시험에서 측정하지 않았습니다.
